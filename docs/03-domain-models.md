# Етап 3. Domain Models

Доменне ядро не залежить від графічного інтерфейсу та від конкретної бази даних. Воно використовує лише Qt Core, без QtWidgets та QtSql. Якщо інтерфейс повністю змінити, ядро залишиться без змін.

## 1. Сутності предметної області

| Сутність       | Призначення                                                       |
| -------------- | ----------------------------------------------------------------- |
| **Contact**    | Людина, з якою виникають борги                                    |
| **Payment**    | Один запис про борг або повернення: контакт, сума, напрямок, дата |
| **Attachment** | Файл-підтвердження до платежу (фото чека, скріншот)               |

Один контакт має багато платежів, один платіж має багато вкладень.

**Загальні рішення:**

- Єдина валюта: гривня.
- Сума зберігається цілим числом у копійках, щоб уникнути похибок округлення.
- Сума платежу завжди додатна, а знак визначається напрямком.
- Баланс не зберігається, а обчислюється з платежів.
- Повернення боргу це звичайний платіж протилежного напрямку.
- Файл вкладення копіюється в папку застосунку. Видаляється лише ця копія, оригінальний файл користувача ніколи не чіпається.

## 2. Класи для зберігання даних

### `PaymentType` (enum)

| Значення       | Сенс                | Вплив на баланс контакту |
| -------------- | ------------------- | ------------------------ |
| `Lent`         | Я дав у борг        | +                        |
| `Borrowed`     | Я взяв у борг       | -                        |
| `ReceivedBack` | Мені повернули борг | -                        |
| `PaidBack`     | Я повернув борг     | +                        |

### `Money` (value object)

Обгортка над сумою в копійках. Відповідає лише за коректне представлення грошей.

| Член                                 | Опис                                                  |
| ------------------------------------ | ----------------------------------------------------- |
| `qint64 kopecks`                     | Значення в копійках                                   |
| `fromHryvnias(double)`, `toString()` | Конвертація та форматування (наприклад, «500.00 грн») |
| `operator+`, `operator-`, порівняння | Арифметика без втрати точності                        |

### `Contact`

| Поле        | Тип         | Примітка                    |
| ----------- | ----------- | --------------------------- |
| `id`        | `qint64`    |                             |
| `firstName` | `QString`   | Обов'язкове                 |

| `note`      | `QString`   | Необов'язкове               |

Методи: `displayName()` (ім'я та прізвище для показу), `isValid()` (ім'я не порожнє).

### `Payment`

| Поле        | Тип           | Примітка             |
| ----------- | ------------- | -------------------- |

## 3. Класи з бізнес-логікою

Сервіси працюють із сутностями через інтерфейси, а не напряму з базою чи файловою системою.

### Інтерфейси (абстракції)

| Інтерфейс               | Відповідальність                                                                                  |
| ----------------------- | ------------------------------------------------------------------------------------------------- |
| `IContactRepository`    | Збереження та отримання контактів (`add`, `update`, `remove`, `getById`, `getAll`)                |
| `IPaymentRepository`    | Збереження та отримання платежів (`add`, `update`, `remove`, `getById`, `getByContact`, `getAll`) |
| `IAttachmentRepository` | Збереження та отримання вкладень (`add`, `remove`, `getByPayment`)                                |
| `IFileStorage`          | Копіювання файлу в папку застосунку та видалення такої копії                                      |

### Сервіси

| Клас                | Єдина відповідальність                                                                                     | Залежить від                              |
| ------------------- | ---------------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| `ContactService`    | Створення, редагування та видалення контактів, валідація. Видалення контакта каскадно видаляє його платежі | `IContactRepository`, `PaymentService`    |
| `PaymentService`    | Створення, редагування та видалення платежів, валідація суми. Видалення платежу каскадно видаляє вкладення | `IPaymentRepository`, `AttachmentService` |
| `AttachmentService` | Додавання вкладення (копіювання файлу та запис у базу) і видалення (лише копії файлу та запису)            | `IAttachmentRepository`, `IFileStorage`   |
| `BalanceService`    | Обчислення балансів із платежів. Нічого не зберігає                                                        | немає (приймає платежі як вхід)           |

### Як рахується баланс (`BalanceService`)

- **Баланс контакту** це сума `signedAmount()` усіх його платежів. Додатне значення означає «винен мені», від'ємне «я винен».
- **Мені винні** це сума додатних балансів контактів.
- **Я винен** це сума від'ємних балансів (за модулем).
- **Загальний баланс** це «мені винні» мінус «я винен».

Приклад: Андрій +300, Олег −100. Мені винні 300, я винен 100, загальний баланс +200.

## 4. Дотримання принципів SOLID

| Принцип                      | Як дотримано                                                                                                                                                                                                                 |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **S**: Single Responsibility | Сутності лише зберігають дані та перевіряють свою коректність. `BalanceService` лише рахує, `AttachmentService` лише керує вкладеннями, репозиторії лише працюють із сховищем. Жоден клас не змішує логіку, дані й інтерфейс |
| **O**: Open/Closed           | Нові правила (наприклад, інша валюта чи нова категорія платежів) додаються розширенням, а не переписуванням існуючих класів                                                                                                  |
| **L**: Liskov Substitution   | Будь-яка реалізація `IPaymentRepository` (SQLite або тестова in-memory) підставляється без зміни поведінки сервісів                                                                                                          |
| **I**: Interface Segregation | Інтерфейси вузькі й окремі: репозиторій контактів не знає про платежі, файлове сховище не знає про базу                                                                                                                      |
| **D**: Dependency Inversion  | Сервіси залежать від абстракцій (`I...Repository`, `IFileStorage`), а не від SQLite чи файлової системи. Конкретні реалізації передаються ззовні                                                                             |

## 5. Результат

Ядро складається з 3 сутностей (`Contact`, `Payment`, `Attachment`), допоміжних типів (`Money`, `PaymentDirection`), 4 інтерфейсів і 4 сервісів. На наступному етапі ці класи будуть показані на UML-діаграмі разом із шаром даних та інтерфейсу.
